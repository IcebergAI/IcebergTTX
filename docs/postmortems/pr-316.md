## Root-cause dependency graph

```text
One PR owns snapshot + clone + compare + reports + legacy reconstruction
    |
    +-> Scenario JSON and materialised Inject rows both act as draft truth
    |       |
    |       +-> clone edit does not change runnable rows
    |       +-> destructive reconciliation is added
    |               |
    |               +-> custom rows deleted or duplicated
    |               +-> schedule overrides need provenance flags
    |               +-> team/audience reconciliation spreads to members/comms
    |               +-> more parent/child locks and rebind paths
    |                       |
    |                       +-> inverted lock orders and launch races
    |
    +-> snapshot omits configuration that runtime still reads mutably
    |       |
    |       +-> LLM, schedules, custom injects, communications, attachments added
    |               |
    |               +-> clone semantics expand with every added field
    |
    +-> migration tries to reconstruct launch state from current rows
            |
            +-> fabricated LLM/inject/communication provenance
            +-> seeded/custom heuristics and schema-version ambiguity
            +-> legacy clone promotion creates duplicates and stale content
```

The loop therefore did not consist of 72 unrelated mistakes. It was a small number of
architectural choices repeatedly expressing themselves through new symptoms.

## Why convergence failed

1. **The PR had no single configuration authority.** Editing Scenario JSON required
   destructive synchronization into materialised rows, while runtime and reports read a
   mixture of both. Each new captured field expanded the reconciliation surface.
2. **Clone semantics were discovered through bugs.** Whether to copy custom injects,
   schedules, communications, attachments, audiences, removed rows, and draft state was
   inferred from existing tables rather than decided first.
3. **Legacy exactness was impossible.** Migrations repeatedly promoted current database
   rows into alleged launch truth. Adding nullable provenance flags made uncertainty more
   elaborate without creating missing history.
4. **Local fixes moved the failure.** Reseeding fixed stale rows but deleted custom work;
   preserving rows created duplicates; provenance flags misclassified legacy rows;
   rebinding fixed clone edits but added authorization and lock-order paths.
5. **The reviewer had no convergence state.** It re-reviewed each head as a new complete
   change, accumulated wording-based prior blockers, and emitted exact duplicates—even
   twice in one review—without changing the engineering recommendation.
6. **Scope never reset.** Clone, report, comparison, migration, attachment durability, and
   concurrency continued to grow inside the same branch after the third blocker round.

## Disposition

`SUPERSEDE_AND_REBUILD` is lower risk than salvage:

- the clean launch foundation has one new snapshot table and one migration rather than
  four migrations and clone reconciliation across many subsystems;
- it implements only the first independently provable capability;
- legacy runs are labelled `unknown` instead of reconstructed;
- clone/report/comparison semantics are decisions for dependent issues, not side effects;
- it starts from current `main` and reuses requirements, invariants, and selected test
  ideas—not #316 implementation code.

The later unreviewed commits on #316 may address individual observations, but proving all
their interactions would be harder than reviewing the bounded replacement. They remain
forensic evidence, not accepted code.

The replacement work is tracked by #317 (launch snapshot), #318 (reports/exports), #320
(clone/lineage/comparison), and #319 (legacy compatibility), with #315 retained as the
parent outcome.

## Recovery guardrail

After each future review round ask: *is the implementation converging toward a simpler
proven design, or accumulating patches?* Three blocker rounds, repeated fix-induced
regressions, material diff growth, repeated failure of one invariant, or new migrations
added mainly to satisfy review comments require an architecture reassessment. At that
point the engineering agent stops patching and re-derives the design from the invariant.

For #316 that point was before review round 4 at `484d7e7`: three blocker rounds had
already occurred and the diff exceeded 1,000 effective lines. Continuing through round 17
cost 13 additional ordinary review/fix rounds.
